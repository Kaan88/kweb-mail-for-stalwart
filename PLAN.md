# Plan

Written 2026-11-12. Nothing is built yet. This file is the agreed starting point; change it when a decision changes.

## Goal

A simple native Android mail client for a Stalwart server, with a Rust core and a Kotlin interface.

The first priority is notifications:

- New mail shows a notification within a few seconds, with the screen off.
- A notification disappears by itself when the mail is read, archived or deleted on any other device.
- The app can show the user, at any time, whether delivery is working.

Design and scope were agreed from [design/mockups.html](design/mockups.html); the look moved to Material You later (see Decisions).

## Layout of the repository

```
core/                  Rust crate (kweb-core)
  src/auth             OAuth, token renewal
  src/jmap             requests; jmap-client for mail, own types for calendars and contacts
  src/store            SQLite cache: mailboxes, messages, state strings, outbox, shown notifications
  src/sync             Email/changes, Mailbox/changes, full resync when the server cannot give changes
  src/push             EventSource stream, re-arm, backoff
  src/notify           decides which notifications should exist
  src/actions          mark read, archive, delete, send; queued when offline
  src/ffi.rs           the UniFFI interface
  tests/               against a mock JMAP server
cli/                   small desktop program that drives the core against a real server
android/               Gradle project
  app/                 Compose screens, services, receivers
design/                mockups
branding/              Ward assets
```

The Kotlin side never talks to the server. It calls the core and renders what the core returns.

## The notification rule

The core holds one rule: **the notifications on screen must equal the unread Inbox mail that arrived after sign-in and that the user has not swiped away.**

Each time the rule runs, the core compares that set with what it last told Android to show, and returns two lists: post these, cancel these.

It runs when:

1. the server pushes a state change (new mail, or a change made on another device),
2. the connection is re-established,
3. the 15-minute background check fires,
4. the app comes to the foreground,
5. the phone finishes booting.

Details that make it hold:

- The shown set is stored in SQLite, so a killed process does not forget what is on screen.
- A notification's Android id is derived from the message id, so posting twice updates instead of duplicating.
- A swipe-away is recorded, so that mail is not posted again.
- Removal is silent. Only a genuinely new message makes a sound.
- Actions (the user's choice of up to three from Archive, Delete, Mark read, Reply; default Delete, Mark read, Reply) go through the core, also when the app was not running.

Android pieces:

| Piece | Job |
|---|---|
| Foreground service | Holds the EventSource connection. Shows the silent "Connected" entry. |
| WorkManager job, every 15 min | Runs the rule and restarts the service if it was killed. |
| Boot receiver | Starts the service after a restart. |
| Action receiver | Handles notification buttons and swipes. |
| Channels | Mail, Reminders, Connection (silent). |

To check at milestone 2: the foreground service type (`specialUse` is the plan, because Android 15 limits `dataSync` services to 6 hours a day), and how the target phone's maker treats exempted apps.

### M3: reading

Inbox, threads, message view (HTML in a sandboxed WebView, remote images off by default), folders, search, swipe actions, offline reading of recent mail.

Built 2026-11-14 (not committed at the time of writing). How it was decided:

- **Lists are conversations.** A row is a thread's mail in that folder; the thread screen shows the whole thread, replies in Sent included (`Thread/get`, then the headers that are missing).
- **Bodies come from `Email/get` body values, not from the raw message.** The server has parsed the MIME already and the request carries no attachments. The raw message's blob id is stored with the body, so M9 can fetch the RFC 5322 bytes when it needs them (this replaces "keep the raw bytes" in M9 stage 0).
- **Offline reading:** the bodies of the newest 100 Inbox mails are fetched after a notification pass, beside the live loop and never in its way, plus every message that was opened. Attachments and inline pictures are fetched when shown and kept in the app's cache directory.
- **Each folder has a window:** the cache holds it without gaps back to a date, and the list shows only that part; "load older" moves the window. Without it, an old mail fetched by a search or a thread would appear in the list with a gap above it.
- **HTML is not cleaned in the core.** The WebView has scripts off, no file or content access, a content security policy, and every request goes through one policy: `cid:` pictures from the mail, remote content only after "Show" for that message (network loads are blocked in the view until then), links open in the browser on a tap only.
- **New actions:** star, move to a folder (also Spam and Undo of a swipe). A change the server refuses for good is dropped from the queue and the message is shown again as the server has it.
- **Search** is the server's (`text` filter); offline it falls back to the cached senders, subjects and previews and says so.
- **Left for M4:** Compose and reply buttons, Settings. Not done in M3: marking the matched words in search results, a per-sender "always show images".

Checked on the emulator against the local Stalwart: list, folders drawer, a four-mail thread, HTML with a remote image (hidden, then shown), an inline picture, swipe to archive with Undo, search on the server, reading a prefetched mail with the server cut off. Not checked there: opening and saving an attachment, Move to, load older on a large folder, the dark theme, a notification tap opening its thread. Not checked on the real phone at all.

### M4: sending

Compose, reply, forward, attachments, drafts on the server, sender identities, undo send, recipient completion from the address book, quota in Settings.

Built 2026-11-14. How it works:

- **A draft lives in the cache from the first keystroke** (`core/src/compose`, `store/drafts.rs`) and a pass copies it to Drafts on the server; an edit replaces the server copy. A user write never creates a draft row, so a late save or a second tap on Send cannot bring back a message that was sent.
- **Send holds the message back for 10 seconds on the phone** (Undo), then a pass submits it. The states are draft, sending, submitting. Only the exact version that was copied to the server is submitted. A send whose answer was lost is settled by asking the server whether it holds a submission of that copy, so nothing is sent twice. Any definite refusal gives the draft back with the reason.
- **Outgoing mail comes after the notifications in a pass**, and the identities and the address book are fetched beside the loop: sending can never delay or fail a notification.
- **Replies and forwards are built in the core** (recipients, "Re:"/"Fwd:" once, the original quoted as text, threading headers, the signature). Writing is plain text.
- **Android:** a Compose screen with recipient chips and suggestions, attachments, autosave; the Compose button on the list; the connected Reply / Reply all / Forward bar on a thread; a Reply action on the notification; a Settings screen (account, storage, theme, Delivery check, sign-out, which now warns about unsent mail).

Checked on the emulator against the local Stalwart ([design/m4-emulator.png](design/m4-emulator.png)): write and send a message to the test account, the Undo bar, its arrival after the hold, the reply bar and a prefilled reply, Settings. Not checked there: Undo itself, attachments, Cc/Bcc, suggestions, the notification's Reply action, a refused send, drafts opened from the Drafts folder, several identities. The local server reports no quota, so the storage bar was not seen. Not checked on the real phone.

**Release 0.1.0** after M4: phase 1 of the scope.

### M5: calendar

Agenda and day views, create and edit events, repeat rules, invitations, tasks.

Built 2026-11-14. How it works:

- **The agenda is asked from the server each time** and kept in the cache for offline use (`core/src/jmap/calendars.rs`, `jscal.rs`, `store/calendar.rs`). Stalwart 1.1.0 neither expands repeating events in a query nor takes more than one calendar per query, so the core fetches the events of the visible calendars whole and expands the rules itself (`recur.rs`: daily, weekly, monthly, yearly, with interval, count, until, weekdays, month days and set positions). Time zones come from the `chrono-tz` crate (`clock.rs`).
- **One event** is read as the series or as one occurrence (`Core::event(id, recurrence_id)`), with that occurrence's own time, title and place.
- **Writes are patches of what the app owns** (title, time, zone, length, place, notes, reminders, a simple repeat rule, the calendar). Everything else on the server stays: participants, other calendars, a rule the app cannot edit. A write carries the state it was read at and is redone once if the event changed meanwhile. Moving a series moves its exceptions with it.
- **Invitations** are answered in the calendar (the server tells the organizer); **tasks** are ticked off in the agenda.
- **A reminder notification** opens the occurrence it is for and goes away when opened.
- **Android:** the bottom bar (Mail, Calendar) on the two root screens, the agenda with a week strip, the event screen, and a form for creating and changing entries.

Not built: the day view (the agenda with its week strip stands in for it), answering an invitation from the mail that carried it, showing or hiding single calendars, creating calendars.

Checked on the emulator against the local Stalwart ([design/m5-emulator.png](design/m5-emulator.png)): the bottom bar with the unread badge, the agenda with two timed events, an all-day event, a five-day series and a task, in the phone's time zone, and the screen of one occurrence of the series. The emulator ran without acceleration (the owner's VM was up) and was too slow for more. Not checked there: creating, changing and deleting an entry, ticking a task, answering an invitation, the reminder tap, the offline agenda. Not checked on the real phone.

### M6: contacts and away message

### M7: sharing, files, second push route, AI assistant

Shared mailboxes and calendars, file storage, and UnifiedPush as an optional transport. And an AI assistant.

**AI assistant.** Researched 2026-11-14 from the owner's Thunderbird extension (AI Assistant 1.2.3), Bulwark's AI Assistant plugin and Stalwart 1.1's docs and source.

- **Where the model runs.** Stalwart's AI is server-internal: an `AiModel` object (managed over JMAP as `x:AiModel/*`) feeds only the spam classifier and the Sieve function `llm_prompt`. No documented JMAP or HTTP call lets a client send a prompt to it, and it is an Enterprise feature. So the app calls a provider itself, from the Rust core, as Bulwark and the Thunderbird extension do. A "use my server's model" mode is possible only if Stalwart adds an endpoint. Not verified: that none exists (absence in the docs is not proof).
- **Providers.** Two adapters, both streaming with tool calling: OpenAI-compatible (`POST {baseUrl}/chat/completions`, key optional so Ollama, LM Studio and vLLM work over the LAN or a VPN; hide `<think>` output; retry without tools if a 400 mentions tools) and Anthropic Messages (`/messages`). Base URL, key and model are set by the user. Keys go through the existing secret-store callback (Android Keystore), never plain settings or logs. The extension's "Claude on this computer" mode has no phone equivalent and is left out. **Correction, 2026-11-15:** this line was the plan, not the state. Stage 1 and round 2 had no tool calling at all (no `tools` in a request, one user turn only, no retry without tools). It was written with stages 2 to 4 (`chat_parts` and `converse` in `core/src/assistant/provider.rs`; the retry is for the OpenAI protocol only) and has run against the mock service only; see "Decided without asking", M7.
- **Privacy (from Bulwark).** Nothing is sent until the user taps. A first-use confirmation names the service, host and model. Per-feature switches. Hard caps: about 60,000 characters and 8 pictures per request, 20 messages per thread summary, about 12,000 characters per mail body. Remote images are never loaded. **Not built (2026-11-15):** picture input. No request carries a picture, so the cap of 8 pictures caps nothing; the other caps are in the code.
- **Safety (from both).** Mail and tool results are wrapped in tags and declared to be data, not instructions. The assistant never sends or deletes on its own: a draft opens in the composer, and any change asks first (an approval card showing what will happen) with Undo. The extension's four risk classes (read, ui, change, confirm) and its cap of 30 agent steps carry over.
- **Stages.** (1) Summarize a message or thread, draft a reply, and a compose sheet to rewrite, shorten, change tone, fix spelling and translate. (2) Reply ideas, to-do and date extraction, explain a selection. (3) A chat screen whose model looks things up through tools over the JMAP code already in the core (search, read, list folders, calendar). (4) Actions (archive, move, mark, tag, add events) with ask-first as the default.
- **Left out.** Bulwark's files area, memory notes, admin-lock config and plugin hooks; the extension's panel docking, Thunderbird calendar and address-book wrappers, and Claude CLI bridge.
- **Stalwart Enterprise.** Checked in the v1.1.0 source (`crates/common/src/enterprise/config.rs`): with no licence key the server returns no Enterprise edition, except in a build made with the compile-time flag `--cfg stalwart_tests`, which grants a one-year licence for 100 accounts on any hostname. It is not a runtime setting, so the official release binary does not have it; a dev server for this app would be built from source with that flag (the licence's section 4.5 allows copying the source for development and testing). Without it, the official route is the 30-day trial. M7 does not depend on either. Owner's decision (2026-11-14): when the AI work starts, build Stalwart from source with that flag as a second local test server (separate data and port, next to the normal one) and port the Thunderbird extension's provider layer, prompts and tools first; a real Enterprise licence comes later and is tested for real then. **Correction, 2026-11-14:** that build was tried and is not possible or permitted; see "Decided without asking", M7.

### M8: filters (a simplified Sieve editor)

Researched 2026-11-14 against Bulwark's source (`lib/sieve/`, `stores/filter-store.ts`, `components/settings/filter-settings.tsx` in bulwarkmail/webmail) and RFC 9661.

- JMAP only (`urn:ietf:params:jmap:sieve`: `SieveScript/get`, `/set`, `/validate`, script text through blobs). No ManageSieve. The section is hidden when the server does not advertise the capability.
- A visual rule builder, as in Bulwark. First version: conditions From (address or domain), To/Cc, Subject and one custom header, match all or any; actions Move to folder, Mark read, Star, Delete (discard) and Stop. Left out at first: regex, body, size and attachment tests, wildcard matches, activation periods, drag and drop (up/down buttons instead).
- Rules are the source of truth, stored as JSON in a versioned metadata comment at the top of one script, followed by the generated Sieve (Bulwark's approach). The builder never parses arbitrary Sieve. A script without valid metadata is foreign: shown read-only or as raw text, never overwritten silently, with a warning that activating ours would deactivate it (JMAP allows one active script). One managed script, named `kweb-filters`.
- Always `SieveScript/validate` before saving and show the server's error text; save per change and restore the old state on failure; delete with Undo. Gate constructs on the session's Sieve capability (extensions, `maxNumberRedirects`: forward is hidden at 0; script size). Move rules get a spam guard unless "include spam" is on.
- "Create a rule from this message" on the message screen (sender, domain, List-Id) is the mobile-friendly way in; new rules go on top.
- The away message is its own simple screen on `VacationResponse` (M6). Stalwart stores it as a reserved script named `vacation`, and enabling it displaces the user's active script, so the editor treats that script as read-only and warns about it.
- A raw editor is an advanced option, read-only with copy at first; saving by hand marks the script hand-edited and turns the builder off until a confirmed reset.
- The core gets: list scripts, get and put text, validate, activate, deactivate, delete, rename, and the rule list with its Sieve generator, all tested against the mock server and the local Stalwart. Stalwart's error names (`invalidScript`, `scriptIsActive`) differ from the RFC's (`invalidSieve`, `sieveIsActive`): accept both and check on the test server.
- Stalwart's limits are low (one redirect and three outgoing messages per run, a script size cap): check the generated rules against them.

**Built 2026-11-14.** Settings has "Mail filters": a switch, the rules in order with up, down and a switch each, and an editor (all or any of: From, To or Cc, Subject, another header; contains, is, begins with, ends with; then move to a folder, mark read, star, delete, stop). "Filter mail like this" on a message starts a rule from it. The rules are stored as JSON in a comment at the top of the one script the app owns (`kweb-filters`), followed by the Sieve generated from them; the app never parses Sieve, and a script that is not byte for byte what the rules give counts as edited by hand and is only replaced after a confirmation.

- Decided without asking: filters and the away message exclude each other (the server runs one script) and both screens say so; a folder is named in the script by its path and looked up again from its id at every save, so a renamed folder shows as "out of date" with an Update button and a deleted one blocks the save; Delete moves to the Trash; "From" looks at the whole From line, "To or Cc" at the addresses; no spam check, no forward, no body or size tests in this version; a write is refused unless the filters were read first in the same run, so a change made elsewhere is never overwritten.
- Checked: 818 core tests (with property tests that nothing a user types can add a statement to the script) and 769 Android unit tests. On the local server with the CLI as the tester: add a rule from a message, switch on, read the script back, change it while active, switch off. On the emulator as the second user: a rule made in the editor (From contains, mark read, star), switched on, and a mail then sent to that user arrived marked read and starred.
- Not checked: move to a folder and Delete on real delivery, the banners for a foreign script and for a hand-edited one on a device, reordering, "Filter mail like this".
- Left on the test server: the tester and the second user each have a `kweb-filters` script, switched off.

### M9: optional S/MIME and OpenPGP

For people who use them; the owner does not. Off by default and independent of the server: it works over plain JMAP (`Email/get`, blob download), so nothing here needs Stalwart's help. Stalwart's own encryption is at rest only: the user uploads a public key, the server encrypts incoming mail with it, and it never holds a private key. Researched 2026-11-14; the sizes are estimates, not sourced.

| Stage | What | Rough size |
|---|---|---|
| 0 | Fetch the raw RFC 5322 bytes by the blob id M3 stores with each body, and parse MIME with exact signed byte ranges. A spike proves the chosen crates build with cargo-ndk for arm64 and x86_64. | with M3 |
| 1 | Read-only verify: `multipart/signed` (PGP and S/MIME) and a small status chip; a keyring of public keys and certificates in the core database. Likely stack: rPGP (`pgp` crate) for OpenPGP; RustCrypto `cms`/`x509` crates for S/MIME. | 3 to 4 weeks |
| 2 | Decrypt: import private keys (armored PGP, PKCS#12) through the file picker, wrapped by an Android Keystore key, held in Rust only for the call and zeroized after. Detect mail Stalwart encrypted at rest and say that its bodies cannot be searched on the server. | 2 to 3 weeks |
| 3 | Compose: sign and encrypt, including to the sender's own key so Sent stays readable; avoid double encryption with Stalwart's gateway. | 3 to 4 weeks |
| 4 | Key discovery and trust: Autocrypt headers, WKD, trust on first use with warnings when a fingerprint changes; show where a key came from. | 2 to 3 weeks |
| 5 | Only if asked for: hardware tokens, certificate chain validation against the system store with revocation. | |

Not planned: depending on OpenKeychain (maintenance mode, GPL).

**Stages 0 to 4 are built (2026-11-16); 5 is not.** Stages 0 to 2 (reading) are described first, then stage 3 (sending) and stage 4 (key discovery and trust) below the list. How reading works:

- **Off by default and free when off.** A switch per account in Settings, "Encryption (S/MIME and OpenPGP)" (kv key `crypto_enabled`). Sync never looks at a message for this. With the switch on, opening a message asks the server for its type structure only (`Email/get` with `bodyStructure`, one small request; `core/src/jmap/crypto.rs`); only a message that is `multipart/signed`, `multipart/encrypted`, `application/pkcs7-mime` or has armored OpenPGP text in the body gets its raw RFC 5322 bytes fetched (blob, limit 40 MB: larger is refused, never cut).
- **Exact bytes.** `core/src/crypto/mime.rs` is a small bounded MIME reader that keeps the byte range of every part as transmitted; the signed bytes of a `multipart/signed` are the first part, line ends made CRLF, nothing rebuilt. Decoding text (charsets, HTML) is `mail-parser`.
- **Stack (all pure Rust, cross-compiled with cargo-ndk for arm64 and x86_64 before any code was written):** `pgp` (rPGP) 0.21.1 without its default `bzip2` feature (a C library), `cms` 0.2.3 + `x509-cert` 0.2.5 + `rsa` 0.9 + `p256`/`p384` (RustCrypto) for S/MIME, `p12-keystore` 0.4.1 for PKCS#12, `aes`/`cbc` for CMS decryption, `mail-parser` 1.0.1 (Stalwart's own) for decoding, `zeroize`. rPGP could not be used with bzip2 compressed mail; that is rare and reported as unreadable.
- **Signed mail (stage 1):** OpenPGP detached and clear-signed, S/MIME detached and opaque signed data. RSA PKCS#1 v1.5 and ECDSA P-256/P-384 with SHA-256/384/512; SHA-1 and RSA-PSS are reported as "cannot check" in words. The keyring is two tables (migration 9, additive, no resync): public keys and certificates (never a private part), and the fingerprint first seen for each address.
- **The status is honest** (`core/src/crypto/analyze.rs`, words in `ui/crypto`). Good news only for: a valid signature, from a key the user has in the keyring, whose address is the From address. Otherwise one of: key changed since first seen (trust on first use, never replaced), valid but from a different address, certificate that only came with the message ("signed, certificate not checked against an authority": never "trusted"), key revoked or expired when it signed, unknown key, invalid, unsupported, unreadable. A status says when it covers only part of the message (a signed part inside a wider message), and clear-signed text shows only the signed text. A key found in a message (`application/pgp-keys`, the certificate inside an S/MIME signature) is offered, never added by itself.
- **Decrypting (stage 2):** PGP/MIME, inline PGP and S/MIME enveloped data (RSA key transport, AES-128/192/256-CBC). Private keys: an armored or binary OpenPGP secret key, or a PKCS#12 file (RSA only), imported through a file picker (Android) or a path (`kweb crypto import-private`). The private part is stored only in the host's secret store (on Android, the Keystore-sealed store), as base64 of the OpenPGP key packets (still locked if it was) or of the PKCS#8 key; the PKCS#12 passphrase is used once and not kept. It is read into memory for one call, held in zeroizing buffers, and never goes to the database, a log or an error. A passphrase is asked when a message needs it, from the page the pager has settled on only; "keep unlocked on this phone" stores it in the secret store (and is said to reduce protection); "ask again" deletes it. Removing a key, switching off with "remove all", and signing out delete the private parts and kept passphrases.
- **Decrypted content is never written to the cache.** It is made again, in memory, each time the message is opened. The files of a decrypted message are held in memory (the last 8 messages, wiped when replaced or on switching off) and written by `crypto_save_attachment` only when the user taps one, into `cache/attachments/<account>/crypto/`, which is emptied when the thread screen is left and at every start of the app.
- **EFAIL.** OpenPGP data without an integrity packet (the old "symmetrically encrypted data") is refused ("encrypted without protection"), and a failed integrity check shows nothing; rPGP checks the whole message before releasing any plaintext. A decrypted part is shown on its own (the server's body, text and file list are replaced by the core's copy), never merged with the outer message. S/MIME CBC has no integrity protection, so its decrypted (and opaque signed) content is shown alone with remote content off whatever the user's setting is, and the chip says so; the "show pictures" bar is not offered for it.
- **Signed inside encrypted** is verified (OpenPGP one-pass signatures and signed MIME or S/MIME inside), compared with the outer From address.
- **Stalwart's encryption at rest** cannot be told from a sender's encryption by the structure of a message, so every encrypted message carries the note that it cannot be searched by its text on the server, and the Settings screen says it once.
- **CLI:** `kweb crypto status|on|off|keys|import|import-private|rm|check|take|decrypt|lock` (the passphrase comes from `KWEB_PASSPHRASE`, never from an argument).
- **Tests:** messages written by GnuPG 2.4 and OpenSSL 3.5 (`dev/make_crypto_fixtures.py`, files under `core/tests/fixtures/crypto/`, kept byte for byte), not by the code under test: valid, tampered body, wrong signer address, unknown key, changed fingerprint, revoked key, clear-signed with text around it, a signed part in a wider message, missing integrity packet, changed ciphertext, wrong and kept passphrase, signed-then-encrypted (PGP and S/MIME), S/MIME RSA and ECDSA, expired certificate, SHA-1, AES-GCM, PKCS#12 modern and legacy; through `Core` against the mock server, including that no plaintext and no armored private key is in the cache database or its log, and that sign-out deletes the private parts. Size: the release libkweb_core.so for arm64 grew from 12,465,984 to 16,366,840 bytes (+3.9 MB, +31%) with all three stages (measured with cargo ndk --release on the commit before and on this one); the debug APK went from 131,947,042 to 172,138,786 bytes (debug libraries, both ABIs, not shrunk).
- **Not checked (needs a device or real third-party mail):** the screens on a device or the emulator (the Settings screen, the chip and its dialog, the passphrase prompt, opening a decrypted file); mail from Thunderbird, Outlook, Apple Mail, ProtonMail or Delta Chat; BER (indefinite-length) CMS from old programs (only DER is read); S/MIME with elliptic-curve key agreement, RSA-OAEP and AES-GCM (reported as unsupported in words); keys that are not RSA for S/MIME decryption; PGP v6 and post-quantum keys; inline pictures (`cid:`) of a decrypted message (they are listed as files); expired OpenPGP keys (the logic is there, no fixture could be made because GnuPG refuses to sign with an expired key); keeping a passphrase unlocked over a restart.
- **Not built:** chain validation and revocation for S/MIME and hardware tokens (stage 5). Stages 3 and 4 follow.

**Stage 3: sign and encrypt on sending (built 2026-11-16, never seen on a device).** `core/src/crypto/{plan,build}.rs`, `core/src/ffi/crypto_send.rs`, `core/src/jmap/import.rs`, android `ui/compose`.

- **Per message.** With the account's encryption switch on and a private key for the sending address, the compose screen shows Sign and Encrypt (the default for Sign is a setting, "Sign new messages"; a reply to an encrypted mail starts with Encrypt on). The protocol is chosen by `crypto::plan::resolve` from the keys of the sender and of every recipient (OpenPGP first, then S/MIME); the compose screen and the send use the same function. When the recipients cannot all be reached with one protocol the screen says which addresses have no key and nothing is sent.
- **OpenPGP:** PGP/MIME (RFC 3156), sign-then-encrypt, integrity protected (rPGP, SEIPD). **S/MIME:** detached `multipart/signed`, and enveloped data (RSA PKCS#1 v1.5 key transport, AES-256-CBC, the signature inside), exactly what stage 2 reads. S/MIME encryption is weaker than OpenPGP's (CBC has no integrity protection and PKCS#1 v1.5 key transport has a known padding-oracle weakness for the recipient); it is built because every S/MIME program uses it, RSA-OAEP and AES-GCM are not built, and the compose screen names the protocol.
- **Always to the sender's own key too**, so Sent stays readable. **Bcc:** OpenPGP hides the recipients' key ids in the packets (the message names nobody), and the envelope carries everyone; S/MIME names every recipient in the message, so a Bcc with S/MIME encryption is refused with a reason. A protected message has no Bcc header at all. **Attachments** are inside the protected part. **Subject and addresses are in clear** (the screen says so); protected headers are not built.
- **Drafts:** a draft that is to be encrypted, or that quotes decrypted text, is kept on this phone only and is never saved to the server (a copy made before is removed); the screen says so. The text of such a draft is in the phone's cache until it is sent or discarded, like any draft. Replying to an encrypted mail quotes its decrypted text only when a passphrase was already kept; otherwise nothing is quoted. A reply that quotes decrypted text and is not encrypted asks before sending.
- **The sending rule (never twice, never lost).** The finished message is made once, in the user's own `send`/`schedule_send` call (`ffi.rs send_with`, `schedule_with`, through `protected_message`), after all checks and before anything is stored as sending or handed to the server, and is stored in the same statement that makes the row `sending` (`Store::draft_send_protected`, migration 10, column `drafts.raw`). Every later try (`compose::flush::make_copy`) uploads those same bytes with `Email/import` (`jmap/import.rs`), so a retry never produces a second, different message (same Message-ID, same signature); a row that asked for protection and has no stored bytes is refused, never sent as plain text. A missing key, passphrase, recipient key or an unreadable file stops the call with the draft untouched and a plain error. Send later builds the message once at scheduling time and signing is not redone. Taking a protected message back makes a signed one a draft again with Sign on; an encrypted one stays in Drafts as it is, because it cannot be edited.
- **Passphrase** for a locked signing key: the same prompt as stage 2, asked when Send is tapped and before the Undo countdown starts ("keep unlocked" is stage 2's).
- **The assistant** only gets and sets text: it never sees the decrypted content of a message it was not already allowed to see (the core reads decrypted text only for the quote of a reply the user started), and no `ai_*` call changes Sign or Encrypt (the flags are the user's, set on the draft the compose screen sends).
- **Stalwart's encryption at rest.** Not verified against Stalwart's source: Stalwart encrypts stored mail with the user's own key; what we send is encrypted for the recipients, so a copy in Sent or Drafts may be encrypted a second time by the server. That costs only space and search and exposes nothing.
- **Checked:** unit tests of the builder (read back by stage 1 and 2 code, Bcc not named, locked and wrong passphrase, revoked recipient key, S/MIME), the plan, and `core/tests/suite/crypto_send.rs` through `Core` against the mock server (a retry after a failed upload is one message, a held message retried after a failed hand-over is one and can be undone, a recipient without a key stops before anything is stored, a draft that is to be encrypted is never on the server, a row without its bytes is not sent, send later); `dev/check_crypto_built.py` has GnuPG 2.4 verify and decrypt the PGP/MIME messages and OpenSSL 3.5 verify and decrypt the S/MIME ones (all pass on the development machine).
- **Not checked:** the compose screen on a device, mail read by Thunderbird, Outlook, Apple Mail or Delta Chat, S/MIME with a certificate chain, how Stalwart treats an encrypted message in Drafts.

**Stage 4: key discovery and trust (built 2026-11-16, never seen on a device).** `core/src/crypto/{autocrypt,wkd}.rs`, `core/src/ffi/crypto_trust.rs`, migration 11 (`crypto_keys.verified`).

- **Autocrypt.** With the feature on, opening a message already asks the server for its type structure; the same request now also returns the From address and the `Autocrypt` header (no extra request, nothing at sync). Exactly one header whose `addr` is the one From address and whose key is one usable OpenPGP key is kept; other headers (an unknown critical attribute, two headers, a different address, a key that cannot encrypt, a key over 64 KB) are ignored. Our own outgoing OpenPGP messages carry an `Autocrypt` header with our public key.
- **Trust on first use, never a green badge.** A key learned from Autocrypt or a directory is stored with its source and the date first seen, at most 5 per address and 500 in all, and never replaces another key. The first fingerprint seen for an address is remembered (stage 1's table); a different key for the same address afterwards is shown in the Encryption settings as a warning (`changed_for`) and in the compose check ("more than one key"), and the first-seen one is the one encrypted to. A signature from such a key is the new state `FirstSeenKey` ("Signed, key first seen in a mail", with a long explanation), never `Verified`; only the user's own "Mark verified" (`crypto_set_verified`, the only thing that sets it) or importing the key by hand makes it `Verified`. Encrypting to an unverified learned key shows a warning in the compose screen. The limit is plain: a mail's From and Autocrypt header are unauthenticated, so the first key seen for an address can be a forger's.
- **WKD** (`crypto_wkd_lookup`, "Look for a key: <address>" in the compose screen when a recipient has no key). One explicit tap per address after a dialog that says the recipient's mail provider learns of the lookup; never in the background. Advanced method first (`openpgpkey.<domain>`), then the direct one. HTTPS only; no redirect is followed at all (stricter than "none to other hosts"); no account credential, cookie or header is sent (a fresh client); answers over 128 KB, plain-IP and one-label addresses and non-ASCII addresses are refused before anything is sent; only a key with a user id for that address that can encrypt is kept. The file name is checked against the specification's example.
- **S/MIME certificates** from signed mail the user opened are still offered by stage 1 and added only by the user's tap (source "from a mail"); the Encryption settings show the source and the first-seen date of every key, its fingerprint, "Mark verified" and Remove, and a key the user imports by hand replaces the weaker source of the same key.
- **CLI:** `kweb crypto send <to> <subject> <text> [--sign] [--encrypt]`, `wkd <address>`, `verify|unverify <key-id>`; `keys` prints the source, the first-seen time, verified and changed.
- **Checked:** `core/tests/suite/crypto_trust.rs` (Autocrypt kept only with the feature on and only when the header is the sender's, single and understood; a second key is a change and the first stays; verified is only set by the user; a key imported by hand replaces the weaker source; the lookup refuses bad addresses and is off with the feature), unit tests for the header parser, for WKD (the specification's file name, URL shape, order of the methods, a key for another address is not believed, a redirect is not followed, the size limit, nothing but a plain GET is sent, plain HTTP refused), `FirstSeenKey` in the analysis, that our outgoing Autocrypt header carries only the public key, and that encrypting to an Autocrypt key warns until verified.
- **Not checked:** a lookup against a real WKD server (the fetch is tested against a local plain-HTTP server, the HTTPS part only by the refusal of plain HTTP), real Autocrypt mail from Thunderbird or Delta Chat, the settings and compose screens on a device. Not built: Autocrypt Setup Messages and gossip, WKD policy files.

**Stage 4 built (2026-11-16): the server's own calendars in the phone's calendar.** Credit: the design follows Bulwark Mobile's device sync (github.com/bulwarkmail/native, AGPL-3.0 with an app store permission; `dev/notes/device-sync-research.md`). Only the design was taken, no code, tests or text; the About screen says so. How it works:
- **Core** (`core/src/jmap/devcal/`: `engine.rs`, `map.rs`, `net.rs`; `core/src/ffi/devcal.rs`). The provider is a UniFFI callback interface `CalendarProvider` (state, calendars, events, `set_sync_data`, purge); the core never sees an Android type and Kotlin never talks to the server. One run: calendars (own, readable, not switched off), then what changed on the server (`CalendarEvent/changes` from the stored state, 256 at a time; a state the server does not know, or a changed set of mirrored calendars, or a changed phone zone, reads everything), then what changed on the phone, then the clean-up and the new state. State, the server's copy of each event (`SYNC_DATA1`) and the row as the sync last wrote it (`SYNC_DATA4`) are in the provider, so they go with the Android account. Every sync id is `<app account id>/<event id>` (`#<recurrence id>` for an exception, `~pending/<uid>` for an event made on the phone and not yet sent).
- **Merging** is per unit (title, description, place, timing): the phone's change is what differs from the baseline, the server's what differs between the old and the new copy read the same way (so what the provider rewrites on its own is never an edit). Same unit changed on both: the server's. Edit on the phone, delete on the server: the server's delete. Delete on the phone, edit on the server: the phone's delete (the event is destroyed). Upload is a JMAP patch of the changed units made by `jscal::update_patch` on the event read just before, sent with `ifInState` (the existing `change()`, which reads again once on a mismatch); what the phone does not show (keywords, other places, attendees) is never sent. The server's copy is read back after an upload and becomes the row, unless the phone changed the row meanwhile (then it stays dirty). An event made on the phone is claimed first (`~pending/<uid>`, a uid minted here) and an upload whose answer was lost is found again by its uid in the next download and adopted, never made twice.
- **Series** are written read-only: RRULE (from `recurrenceRule`; another calendar than Gregorian, a skip, a leap month or an excluding rule is shown once and read-only), EXDATE for excluded occurrences, one exception row per changed occurrence. A phone edit, delete or new exception of a series, or any edit in a read-only calendar, is put back from the server's copy and counted; a new series made on the phone is left alone and counted (`not_sent`). Reminders are not written (`MAX_REMINDERS` 0), tasks are not mirrored, shared accounts and calendars are never touched.
- **Guard.** More than 50 deletions and more than a fifth of the events, from the server's side (in calendars that are mirrored) or from the phone's, stop the run before any of them is done and say so (`StoppedTooManyDeletions`); a full read that finds no event while the phone holds more than ten stops as `StoppedServerEmpty`. The state is not advanced. There is no "review deletions" screen: the screen says to switch the feature off and on, which starts from the server.
- **Push.** The live connection now also listens to `Calendar` and `CalendarEvent` and calls the new `Listener.calendar_changed()`; Android asks for a sync of the account (at most one a minute). Not done: the Google push road (its types are unchanged), so in Google mode only the hourly sync, the foreground and the phone's own edits trigger a sync.
- **Android** (`android/.../devcal/`, `ui/devcal/`). One Android account per app account (type `ovh.kweb.mail.account`, the authenticator holds no secret and "add account" opens the app), a sync adapter for `com.android.calendar` in the app's process (`isAlwaysSyncable` false, user visible), `CalendarContractProvider` as the port (every write as a sync adapter; titles and places never in a log or error), Settings > Calendar > Device calendar (switch, rationale dialog then `READ_CALENDAR` and `WRITE_CALENDAR`, a switch per own calendar, last run, Sync now), a periodic sync every hour, a sync on push, one when the app comes to the foreground, and Android's own upload sync shortly after an edit in a calendar app. A run that stops or fails (not for an unreachable server, which the framework retries) posts one notification per account on the "Calendar sync problems" channel that opens the screen. Switching off uploads what is waiting (best effort), then removes the Android account, which removes the calendars; removing the app account does the same; an Android account the user removed in Android's settings turns the switch off and is not made again.
- **Decided without asking:** the sync state lives in the provider (`SyncState`) and not in the core's cache; `Calendar/changes` is not used (the calendar list is small and read in full each run, only differences are written); a calendar is on until the user switches it off (`devcal_off` in the core's key/value table); notifications only for a stopped or failed run, not for a missed network; `READ_SYNC_STATS` is in the manifest because the screen asks whether a sync is running (found by a crash on the emulator).
- **Checked.** Core tests against the mock server with a fake provider (`core/tests/suite/devcal.rs`, 11 tests): the mirror and its second run writing nothing, the changes feed (edit, delete, create) and a lost history, a shared calendar and a switched-off calendar never in the provider, an edit uploaded as a patch that leaves keywords and places alone, same-unit conflict and different-unit merge, the two delete rules, an event made on the phone made once and one adopted by uid, series and read-only calendar edits put back, both guards; mapping tests in `map.rs`; Kotlin tests for the column mapping and rules. On the emulator `kweb35` against the local server (the image has Google Calendar, which needs its first-run set-up, so the provider was read with `adb shell content query` instead): switching on asked for the permission after the dialog, the calendar and a timed, an all-day and a weekly event with an excluded date and a moved occurrence appeared; an event inserted in the provider (as a calendar app would) reached the server once with its uid; a title edited on the phone and a time and title edited on the server crossed over; a delete on each side crossed over; switching off removed the Android account and every row. The tester's calendar was left empty.
- **Not checked:** the owner's phone; a real calendar app's edits (Google Calendar, Etar, Fossify behave differently from `content update`), a series edited in one, the notification of a failed run and its tap, permission revoked while on, the removal of the app account with the feature on, a second account, a calendar on the server that is read-only, the 30-second upload sync Android schedules itself (a sync was started by the app coming to the foreground), the periodic hour, a push-triggered sync, DST edge times, descriptions over 64 KB, and Google push mode. ## Reused from Postern

Postern (MIT, same author) already has, in Rust: the OAuth flow with client registration and token rotation, the EventSource watcher with re-arm and backoff, and calendar alert fetching. These are ported into `core/`, not rewritten.

## Risks

| Risk | Handling |
|---|---|
| The phone's maker kills background apps despite the exemption | Delivery check detects it and says which setting to change. If it cannot be solved on that phone, UnifiedPush moves up from M7. |
| `jmap-client` has no calendar, contact or file types | Hand-written types in `core/src/jmap`, as Postern does for reminders. |
| UniFFI async and callbacks across the bridge | Proven in M0 before anything depends on it. |
| Hand-written Sieve or scripts from other tools collide with the filter editor | The builder owns one script with a metadata comment and treats anything else as foreign, read-only (M8). |
| Rust crates for PGP and S/MIME are less proven on Android | A build-and-round-trip spike before M9 stage 1 (Thunderbird, GnuPG and OpenSSL as counterparts). |
| Stalwart changes behaviour between releases | The mock server tests pin what the core expects; the `cli` runs against the real server before each release. |

#### M9: encryption (2026-11-16)

Decided without asking while building stages 0 to 2:

- No automatic trust: importing a key only means signatures made by it are checked; a key found in mail is offered, never added. The first fingerprint seen for an address is kept for good (until the user removes that key) and a different one afterwards is a warning, not a replacement.
- Chain validation and revocation lists for S/MIME are stage 5, so an S/MIME certificate that only came with the message is "signed, certificate not checked against an authority", and one the user imported is "valid signature", with a note on every S/MIME result that no chain or revocation was checked.
- A status is judged against the From address only (exact, case-insensitive; no plus-address folding, no Sender header).
- Decrypt on every open, in memory, instead of caching plaintext: it costs a fetch and a decrypt each time but leaves nothing on the phone; the cost of the fetch is bounded by the 40 MB limit.
- Private keys are stored through the existing secret store callback, not a new one. The OpenPGP key is stored with its own passphrase protection intact; PKCS#12 is unpacked at import (its passphrase is not kept) because the core then needs only the PKCS#8 key.
- Only RSA keys can open S/MIME mail (key transport). Elliptic-curve and OAEP and GCM messages are reported as unsupported in plain words instead of failing.
- SHA-1 S/MIME signatures are not accepted (reported as "cannot check"), RSA-PSS is not checked yet.
- The thread screen asks for a passphrase only on the settled page of the pager; a neighbour that needs one waits, and a dismissed prompt can be reopened from the chip.
- Stalwart's own at-rest encryption cannot be told from sender encryption, so it is not named; the "cannot be searched on the server" note goes with every encrypted message.
- Rust `String` passphrases from the host arrive as a Kotlin `String` that cannot be wiped; the core wraps what it receives in `Zeroizing` and the Kotlin side drops it as soon as the call returns.
