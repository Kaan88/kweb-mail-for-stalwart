1. FOLDER MANAGEMENT (Mailbox/set)
Create
- Top level: REQ {"create":{"t":{"name":"zt-top"}}}. RESP created {"id":"bi","totalEmails":0,"unreadEmails":0,"totalThreads":0,"unreadThreads":0,"myRights":{all true},"parentId":null?...}. The create answer only echoes the properties that differ from what the client sent or from the defaults, so check with Mailbox/get when you need parentId, role, sortOrder, isSubscribed. Defaults: role null, sortOrder 0, isSubscribed false (a new folder is NOT subscribed by default).
- Nested: {"name":"zt-parent","parentId":"bi"} works, and so does a creation-id reference "parentId":"#t" inside one request.
- sortOrder and isSubscribed are accepted at create: {"name":"zt-so","sortOrder":7,"isSubscribed":true} created. Update: {"sortOrder":3,"isSubscribed":true} gives "updated":{"id":null}. sortOrder -1 or 4294967296 gives {"type":"invalidProperties","description":"Invalid property or value.","properties":["sortOrder"]}.
- Update answers are "updated":{"<id>":null} for every successful rename, move, sortOrder, isSubscribed, role change.
Roles
- role "important" is accepted on a user folder (the zt-imp folder), and role null is accepted. "Important" (capital I) was accepted on update too, so the server folds case; I did not read back whether it is stored lowercase. A role that already exists on another folder: {"type":"invalidProperties","description":"A mailbox with role 'archive' already exists.","properties":["role"]} (same for inbox, junk, trash, drafts, sent). A role the server does not know ("bogus", "all", "flagged"): {"type":"invalidProperties","description":"Invalid property or value.","properties":["role"]}.
- Existing role folders: renaming works for ALL of them. REQ update {"a":{"name":"InboxX"}} gave "updated":{"a":null}; Trash, Junk, Drafts and Sent were also renamed successfully (I restored every name afterwards). Moving Inbox under another folder also succeeded ("parentId":"v" gave updated). So the client must lock these itself: the server only protects the role and the delete.
- Changing the role of Inbox: {"type":"invalidProperties","description":"You are not allowed to change the role of Inbox, Junk or Trash folders.","properties":["role"]}.
- Destroying Inbox, Trash (b) or Junk (c): {"type":"forbidden","description":"You are not allowed to delete Inbox, Junk or Trash folders."}. Destroying Drafts (empty) SUCCEEDED ("destroyed":["d"]). Sent with mail: {"type":"mailboxHasEmail","description":"Mailbox is not empty."}. Archive (not tried to destroy). So Drafts, Sent and Archive are only protected by the not-empty rule; the client should refuse to delete any role folder itself.
Names
- Duplicate sibling name: {"type":"alreadyExists","description":"A mailbox with name 'zt-top' already exists.","existingId":"bi"}. It is case-insensitive ("ZT-TOP", "INBOX" collide) and applies on create, rename and move. The same name under a different parent is fine (zt-child under bi and under bv).
- Rename to its own current name: updated (no error). Rename onto a sibling's name: same alreadyExists. Move into a parent that already has that name: alreadyExists with existingId.
- Empty or whitespace-only name, or missing name: {"type":"invalidProperties","description":"Mailbox name cannot be empty.","properties":["name"]}. name null on update: "Invalid property or value."
- The server accepts and stores these (no forbidden-character list at all): "zt/a", "zt<a", ".", "..", "a\u0000b", "a\nb", "zt.a.b", and "zt-Türkçe-日本語-😀". The client must validate names itself (suggest rejecting / \ and control characters, since "/" or "." may be a hierarchy delimiter for IMAP).
- Length: 255 bytes accepted, 256 bytes rejected: {"type":"invalidProperties","description":"Mailbox name is too long.","properties":["name"]}. It counts bytes: "é"*128 (256 bytes) was rejected.
- Nonexistent parent: {"type":"invalidProperties","description":"Parent ID does not exist."} (no "properties" key on create).
Depth
- Chain zt-top > d1 > ... : the 10th level is accepted and the 11th fails: {"type":"invalidProperties","description":"Mailbox parent-child relationship is too deep.","properties":["parentId"]} (maxMailboxDepth 10).
Move and cycle
- Move to top level ("parentId":null), move under another folder: updated. Making a folder its own parent: {"type":"invalidProperties","description":"Mailbox cannot be a parent of itself.","properties":["parentId"]}. I did not test a longer cycle (move a folder under its own grandchild).
Destroy
- Empty folder: {"destroyed":["cb"]}. Nonexistent: {"notDestroyed":{"zzz":{"type":"notFound"}}}.
- Folder with child folders: {"type":"mailboxHasChild","description":"Mailbox has at least one children."}, even with onDestroyRemoveEmails true. There is no flag to remove children; destroy the children first. Destroying child and parent together in one request ("destroy":["ca","b3"], children listed first) worked.
- Folder with mail, no flag or onDestroyRemoveEmails false: {"type":"mailboxHasEmail","description":"Mailbox is not empty."}.
- With the method-level argument "onDestroyRemoveEmails":true (REQ {"accountId":"c","destroy":["cc"],"onDestroyRemoveEmails":true}): RESP {"destroyed":["cc"]}. A mail that was in cc only was deleted (Email/get then lists it in notFound). A mail that was in cc AND Archive was kept, now with mailboxIds {"h":true}, so it is only unlinked.
Changes and push
- Mailbox/changes sinceState "sveba" after a run of creates and one role update: {"oldState":"sveba","newState":"sxqba","hasMoreChanges":false,"created":["bv","bw",...],"updated":["bj"],"destroyed":[],"updatedProperties":null}. A folder created and then renamed or moved inside the window is only listed in "created". Updated properties are not narrowed (null), so re-get the whole folder. Counts change state as well: any Email/set that changes totalEmails moves the Mailbox state, so expect many Mailbox/changes from mail activity.
- Push: GET /jmap/eventsource/?types=*&closeafter=no&ping=0 with Basic auth. First event on connect: event: state, data {"@type":"StateChange","changed":{"c":{"Mailbox":"sviba"}}}. About 15 changes made in a burst (create, rename, move, roles, depth chain) produced ONE more StateChange {"changed":{"c":{"Mailbox":"sxqba"}}}, so changes are coalesced. The event names only the data type and state, never ids.

2. JUNK
- Moving a mail Inbox to Junk with REQ Email/set update {"<id>":{"mailboxIds/a":null,"mailboxIds/c":true}} gave updated, and Email/get keywords before and after were identical ({"$hasnoattachment":true,"$seen":true}). The same on the way back to the Inbox. So the server sets neither $junk nor $notjunk on a move, and removes none.
- $junk and $notjunk are plain keywords that the client sets. Both can exist on one mail at once ({"$notjunk":true,"$junk":true} was stored). Importing straight into Junk with no keywords: no $junk added. Importing into the Inbox with {"$junk":true}: stored as given.
- Training: I looked at ~/tools/stalwart-test/logs/stalwart.log.2026-11-14 for lines added during the moves (3005 lines before; only "Message appended via JMAP (message-ingest.jmap-append)" lines appeared) and grepped for spam, junk, train, bayes, classif, learn: nothing. So the log shows no training line; this says nothing about whether the server trains silently at the log level in use. I could not confirm or disprove training. Recommendation for the client: on "Report spam", set keywords/$junk:true, remove $notjunk, and move to the Junk folder (role junk) in one Email/set; on "Not spam", the reverse (set $notjunk, remove $junk, move to Inbox). That follows the JMAP/IMAP convention and works whichever way the server trains.
- The server adds the keyword $hasnoattachment on its own at import.

3. CUSTOM KEYWORDS AS LABELS
- Case folding: the server lowercases. {"Work":true} is stored as "work"; {"Work":true,"work":true} stores one "work"; {"$Label1":true} stored as "$label1"; "\\Seen" is mapped to "$seen". Email/query hasKeyword "ZT-LAB" matched keyword "zt-lab".
- Allowed characters: IMAP-atom style ASCII. Accepted: letters, digits and . , - _ : ; < = @ ! # & ' ` ~ | ? + ^ / [. Rejected (all {"type":"invalidProperties","description":"Invalid keyword.","properties":["keywords"]}): space, tab, ( ) { % * " \ ], empty string, and ANY non-ASCII (türkçe, 日本語, emoji, é). So a user-facing label like "İş" or "Mom and Dad" needs an encoding in the client (for example percent- or base64-style ASCII with a display name stored elsewhere).
- Length: 128 bytes accepted, 129 rejected with "Keywords cannot be longer than 128 bytes." (strings over 255 characters just say "Invalid keyword.").
- Count: 100 keywords on one mail accepted; 101 or more: {"type":"tooManyKeywords","description":"An email cannot have more than 100 keywords.","properties":["keywords"]}. $hasnoattachment appears to be extra to the user's 100 (stored 101).
- Keyword false: {"keywords/zt2":false} and {"keywords":{"zt1":false}} are accepted and the keyword is simply not stored.
- Reserved ones ($seen, $flagged, $draft, $forwarded, $answered, $phishing, $important, $label1) are accepted as ordinary keywords.
- Email/query (all with the subject filter, test mails in the Inbox): hasKeyword "zt-lab" returned exactly the tagged mails; notKeyword returned the rest; hasKeyword + notKeyword together work; an unknown or invalid keyword ("a b") returns an empty list, no error; a wildcard "zt-*" returns nothing. With t1 tagged, t2 a reply in the same thread (untagged), u tagged in its own thread: allInThreadHaveKeyword -> [u]; someInThreadHaveKeyword -> [t1, t2, u]; noneInThreadHaveKeyword -> everything else (not t1, t2, u). A "keyword" filter key gives {"type":"unsupportedFilter","description":"keyword"}. Sorting works: sort [{"property":"hasKeyword","keyword":"zt-lab","isAscending":false}] returns tagged mails first; same for someInThreadHaveKeyword.
- Listing the keywords in use: there is no way. Mailbox/get properties ["keywords"] returns only {"id":"a"} (unknown property dropped); Email/get "allKeywords" is dropped; no capability or method lists them. The client must keep its own label list (a name list on its side, or in JMAP data it owns) and can only discover keywords by reading Email/get keywords from the mails it loads.
- One odd result: in the first query round a freshly imported mail was missing from subject-filtered results although it had the keyword; it showed up in later runs. It might be the search index lagging a few seconds behind an import. A text query right after an import found the mail at once in another test, so I could not reproduce it; treat subject/text results as possibly slightly late after an import.

4. SEARCH SNIPPETS (SearchSnippet/get)
- Request: {"accountId":"c","emailIds":["ryaaaaeo","r2aaaaep","saaaaaeq","seaaaaer"],"filter":{"text":"invoice"}}. It works with the plain mail capability. It can also take "#emailIds" as a back-reference to an Email/query's /ids with the same filter. An unknown extra argument is ignored.
- Answer shape: {"accountId":"c","list":[{"emailId":"ryaaaaeo","subject":"zt <mark>Invoice</mark> about Zebra","preview":"The quarterly <mark>invoice</mark> for the zebra project is attached. Please review the <mark>invoice</mark> before Friday. Filler sentence number one about nothing. ..."}, ...],"notFound":null}. There is one list entry per id; for a mail with no match both subject and preview are null. Unknown ids appear in "notFound":["zzzzzzz"] and the rest of the list is returned. emailIds [] gives an empty list.
- Preview is about 255 characters of body text (cut mid-sentence), starting near the first match (e.g. "for the <mark>zebra</mark> project is attached...") and not from the top of the mail. Subject match: the subject is the full subject with <mark> around the word.
- Conditions that give snippets: text (subject + body), subject (marks the subject, and also gives a preview), body (gives both a subject, if it matches, and a preview), and multiple words ({"text":"quarterly invoice"} marks each word). A quoted phrase {"text":"\"zebra project\""} marks both words. Partial word "inv" matched "Invoice". Diacritics are exact: "şeker" matched "<mark>şeker</mark>" in a Turkish mail but "seker" matched nothing. Compound filters work: AND of {subject:"zt"} and {body:"zebra"} marked both; OR works; NOT gives nothing.
- Conditions that give NO snippet (all null, no error): from, to, inMailbox, hasKeyword, no filter at all, empty text "", and a mail that does not match.
- HTML mail: the HTML is converted to text for the preview (tags and style removed) and the match is marked: "The quarterly <mark>hedgehog</mark> report is ready. Second paragraph &amp; <mark>hedgehog</mark> notes ".
- Escaping: subject and preview are HTML-escaped; the only real tags are <mark>. A subject "zt Fish <b>bold</b> & chips" came back as "zt <mark>Fish</mark> &lt;b&gt;bold&lt;/b&gt; &amp; chips" and body "<script>alert(1)</script>" as "&lt;script&gt;alert(1)&lt;/script&gt;". So the client can render it as HTML or must unescape it itself, and must not treat other tags as markup. The preview keeps a trailing space.
- Limits: I did not hit a count limit (maxObjectsInGet 500 probably applies; not tested above 4 ids).

5. UNSUBSCRIBE HEADERS
I imported five mails with Email/import (not delivered): "both" (smaaaaet), "folded" (sqaaaaeu), "mailonly" (suaaaaev), "comment" (syaaaaew), "none" (s2aaaaex).
- Working: REQ Email/get {"ids":["smaaaaet"],"properties":["header:List-Unsubscribe:asURLs"]} gives "header:List-Unsubscribe:asURLs":["https://lists.example.org/u/abc?x=1&y=2","mailto:unsub@lists.example.org?subject=unsubscribe"] (angle brackets removed, order kept, query kept as is).
- Folded multi-URL header ("<mailto:leave@lists.example.org?subject=Unsub%20me>,\r\n <https://lists.example.org/one>,\r\n\t<https://lists.example.org/two>") gives asURLs ["mailto:leave@lists.example.org?subject=Unsub%20me","https://lists.example.org/one","https://lists.example.org/two"], so folding is handled. A leading comment "(Use this) <https://lists.example.org/c>" gives ["https://lists.example.org/c"]. A mail with no header gives null. A mailto-only mail gives ["mailto:u@lists.example.org"].
- Form ":all" works: "header:List-Unsubscribe:asURLs:all" gives [[...urls...]] (an array per occurrence). Header names are case-insensitive: "header:list-unsubscribe:asURLs" works.
- "header:List-Unsubscribe:asText" does NOT work and fails the WHOLE Email/get: {"type":"invalidArguments","description":"Invalid property Header(HeaderProperty { form: Text, header: \"List-Unsubscribe\", all: false, as_raw: false })"}. So never ask for it. The client must not mix unknown forms into a list of properties.
- ":asRaw" works and keeps the leading space and the fold: " <https://lists.example.org/u/abc?x=1&y=2>, <mailto:unsub@lists.example.org?subject=unsubscribe>" and for the folded one " <mailto:...>,\r\n <https://lists.example.org/one>,\r\n\t<https://lists.example.org/two>". The bare "header:List-Unsubscribe" (no form) gives the same raw string.
- One-click: "header:List-Unsubscribe-Post:asText" gives "List-Unsubscribe=One-Click"; without a form, " List-Unsubscribe=One-Click" (leading space); absent header gives null. The client should check that value, and that there is an https URL, before it POSTs to the URL with body List-Unsubscribe=One-Click (RFC 8058).
- List-Id: ":asText" gives "Weekly News <news.lists.example.org>" and for the quoted one "\"Folded, list\" <folded.lists.example.org>" (quotes kept). ":asRaw" and the bare form keep the leading space. Absent gives null.
- Email/query with the "header" filter did not find these mails by List-Id, List-Unsubscribe or List-Unsubscribe-Post (all returned []), but {"header":["Subject","unsub folded"]} did find one, so the filter works for some headers; do not rely on it for List-* headers. The server does not offer any other way I found to find list mail.
